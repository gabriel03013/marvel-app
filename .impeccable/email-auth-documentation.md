# Email authentication extension

This records the user-requested Firebase email/password extension to the existing native Android app. `DESIGN.md` and `.impeccable/design.json` remain unchanged: the new forms are an ordinary extension of the supplied archive world. Updated `PRODUCT.md`, `SCREENS.md` and `SETUP.md` define the added capability and setup requirements.

## Implementation and visual bindings

Welcome now offers Google, email sign-in and account creation. `AuthScreens.kt` binds one native XML form (`screen_email_auth.xml`) for sign-in, signup and password reset. Signup collects agent name, email, password and confirmation; Firebase creates the account and updates its name, then the existing user repository persists its Firestore profile. Existing accounts return to Home. Recovery calls Firebase's reset-email operation and displays neutral confirmation.

The form inherits paper cream, warm-white fields, ink text and red primary actions. Bebas Neue titles and Space Grotesk controls inherit the existing typography. Existing field/button drawables supply aligned rounded controls; readable copy takes priority over collage texture. Padding is 28dp; fields are at least 56dp high, buttons use the existing 52dp minimum and password visibility has a 48dp target. At widths of at least 600dp, the form occupies a centered 520dp outer column. It remains scrollable on phones and with enlarged text. Native labels, email/password input types, autofill hints, IME actions and a polite feedback live region support platform interaction. These are reused visual primitives, not new design tokens or raster assets.

## State, recovery and password handling

English validation covers malformed email, missing agent name/password, short signup password and mismatched confirmation. Firebase failures produce explicit messages and allow retry; Google failure messages remain distinct. Pending operations show progress, change the submit label and disable form submission and alternative routes. Back remains available while pending. The ViewModel attempt guard rejects abandoned or timed-out late Firebase sessions rather than navigating into an unwanted authenticated session.

Form drafts survive activity rotation and retries in ViewModel memory. Password and confirmation fields disable Android view-state saving; password drafts are not stored in preferences or instance-state bundles. Opening another auth form, leaving with Back, signing out or completing authentication clears passwords. Firebase's normal authenticated-session persistence is separate from these form drafts. A Show passwords checkbox exposes passwords only on request.

## Verification evidence and limits

The implementation owner confirmed successful debug build, unit checks, AndroidTest compilation and lint with zero errors. Final `EmailAuthFlowTest` confirmation passed on phone (10.389s), tablet (12.436s) and enlarged-font phone (10.036s), one complete test per configuration. Logs are `/tmp/archive-auth-confirm-{phone,tablet,font}.log`. The test exercises real Firebase SDK calls against isolated local Auth/Firestore emulators: signup validation, rotation, persisted profile, sign-out, incorrect-password recovery, reset request, successful login, Back during pending login, rejection of its late session and a subsequent retry. This documenting pass inspected source, confirmation logs and captures in `/tmp/archive-auth-confirm-captures/`, including phone signup, tablet incorrect-password feedback and large-font reset confirmation. Initial font-run failures did not recur after diagnostic stages and UI-thread test synchronization; no definitive root cause was established.

After the user authenticated Firebase CLI, the implementation owner inspected production project `marvel-app-72c20`. Identity Toolkit admin configuration confirmed Google enabled and email enabled with `passwordRequired=true`; no provider changes were needed. The project had only the debug SHA-256 registered. The missing debug SHA-1 (`BE:1F:84:65:7A:28:35:BC:72:5F:11:61:B3:2D:97:8C:BF:BF:0D:FA`) was registered successfully through Firebase CLI. The refreshed `app/google-services.json` was verified against `com.example.marvel` and now contains Android (type 1, matching the debug SHA-1) and web (type 3) OAuth clients. `SETUP.md` and `.impeccable/email-auth-verification.json` record this correction. The post-configuration build, unit, lint and AndroidTest compilation command succeeded in `/tmp/archive-auth-production-config-build.log`.

Production Google account login with the rebuilt app has not yet been exercised following the correction. Earlier cancellation occurred after account choice; registering the missing SHA-1 corrects an observed configuration gap without establishing that gap as the sole cause or proving production login success. Emulator reset confirmation establishes the request/UI path, not production inbox delivery or completion of the external reset-link flow. Captures do not establish a complete TalkBack audit. Different debug/release certificates require their own registered fingerprints and refreshed configuration.
